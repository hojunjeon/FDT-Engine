읽을 점 세 가지.

- **`amount_mu` 가 전 프로필의 `기타` 봉투에서 크게 위로 튄다**(A +0.26, B +0.61, C +0.41). 돌발 지출이 `기타` 봉투로 들어가는데 SPEC §6 이 봉투 금액 추정에서 돌발을 제외하라고 하지 않아, `기타` 의 로그정규가 돌발에 오염된다. `기타` 를 통해 시뮬레이터의 일상 소비 금액이 과대평가된다. SPEC 공식대로이므로 코드 결함은 아니지만 **W6 이 알고 있어야 할 함정**이다.
- **C 의 `card_share` 가 전 봉투에서 위로 편향**된다(0.32 → 0.33~0.65, 편의점은 2배). 거절된 체크 소비가 원장에 없어서 **살아남은 표본이 카드 쪽으로 쏠린 것**이다. 잔액이 얇은 사용자일수록 시뮬레이터가 카드 비중을 과대평가하고, 그 결과 즉시 현금 차감이 줄고 `unbilled`(→ 카드대금)가 늘어 **부족 위험 시점이 뒤로 밀린다**. 구조적 편향이므로 W6·W7 이 반드시 인지해야 한다.
- **`elasticity` 는 소표본 잡음으로 상·하한에 자주 붙는다**(A 의료 2.00, B 의료 0.50, D 취미·쇼핑 0.50). SPEC 의 "저잔여일 5일 미만이면 1.0" 가드가 있음에도, 저잔여일이 5~10일 구간일 때 한두 건의 큰 결제가 비율을 지배한다. 필수 봉투(의료·건강)가 2.00/0.50 로 튀는 것은 SPEC S24("필수 봉투는 1.0 근처")의 의도와 정반대다. **가드 임계를 올리거나 필수 봉투를 1.0 으로 고정하는 규칙이 필요하다**(비블로커 N11).

**❌ 홀드아웃 빌드와 잔액 역산의 맞물림 — 깨져 있다.**

`build_engine` 은 `normalize(twin, as_of=effective_as_of)` 로 **원장을 as_of 에서 잘라낸다**(`engine.py:335`). 그 뒤 두 함수가 잘린 원장을 "전체 기간 원장" 인 줄 알고 쓴다.

1. `ledger.account_balance_at` 의 `opening_balance is None` 분기(`ledger.py:492`)는 `balance − Σ(as_of < date ≤ twin.as_of)` 로 역산하는데, 잘린 원장에는 그 구간 레코드가 하나도 없어 **합이 항상 0** 이 된다. 결과:

   ```
   B_card_crunch, --omit-opening-balance, seed 7
     as_of 2026-09-07  liquidity 1,595,700  gt 1,595,700  diff        0
     as_of 2026-08-08  liquidity 1,595,700  gt 1,451,100  diff +144,600  ← 미래 누수
     as_of 2026-07-09  liquidity 1,595,700  gt 1,325,600  diff +270,100  ← 미래 누수
   ```

   `W-INPUT-FUTURE_TX` 는 정상적으로 뜨지만(무시했다고 말하면서) **잔액은 미래를 그대로 반영**한다. SPEC §4.1 "엔진은 as_of 를 바꾸지 않는다(홀드아웃 누수 방지)" 정면 위반이고, PLAN §5.5 backtest·calibration 이 전부 이 경로 위에 있다. `--omit-opening-balance` 플래그가 W1/W2 리뷰(N12) 때문에 일부러 추가된 역산 경로 검증용인데, 정작 그 경로가 엔진에서 무력화돼 있다.

2. `ledger.reconcile`(`ledger.py:518`)은 `opening_balance + Σ원장(≤ **twin.as_of**)` 를 `balance` 와 비교하는데, 원장이 `as_of` 에서 잘려 있으므로 **과거 as_of 빌드는 항상 차액이 난다**:

   ```
   as_of 2026-08-08  →  W-RECON {account 10, expected 1,451,100, actual 1,595,700, diff 144,600}
   as_of 2026-08-08, strict=True  →  FdtError E-RECON  (빌드 자체가 실패)
   ```

   즉 **홀드아웃 엔진은 항상 오탐 경고를 달고 다니고, `--strict` 로는 아예 만들 수 없다.**

두 증상의 뿌리는 하나(원장 절단 시점)이고 고치는 쪽도 하나다: 원장을 전체 기간으로 만들고 `as_of` 필터는 소비 지점(`state._ledger_until` 은 이미 그렇게 돼 있다)에 두거나, `account_balance_at`/`reconcile` 에 as_of 를 명시적으로 넘긴다.

**판정: FAIL (홀드아웃 경로). 그 외 항목은 PASS.**

**`EngineBuildMeta` vs `schemas.result.EngineMeta` 이중 정의 (지적).**

두 모델이 겹치는 필드는 `engine_id`, `as_of`, `engine_version`, `warnings` 4개다. `Engine.run()` 은 매 호출마다 `EngineBuildMeta` → `EngineMeta` 로 손수 옮기면서 `mode`/`seed`/`n_paths`/`horizon_days`/`elapsed_ms` 를 요청에서 채운다(`engine.py:189-199`). 역할 분리 자체는 타당하다 — 전자는 **빌드 시점 불변 메타(dataclass, 재현성 위해 `built_at` 없음)**, 후자는 **실행 시점 메타(pydantic, §9.1 출력 계약)**. Phase 3 부터는 **`schemas.result.EngineMeta` 하나만이 §9.1 `meta` 로 나가고, `EngineBuildMeta` 는 엔진 내부 전용**이라는 것을 명시해야 모드 구현자들이 어느 것을 채워야 하는지 헷갈리지 않는다. 두 가지를 지금 정리할 것.

- **경고 타입이 붕괴한다.** `EngineBuildMeta.warnings: list[FdtWarning]`(dataclass) → `EngineMeta.warnings: list[dict[str, Any]]`(`asdict` 평탄화). 결과 JSON 의 경고가 스키마 없는 자유 dict 가 되어, `fdt validate`(W12)가 검사할 계약이 없다. `schemas/result.py` 에 `ResultWarning{code, message, details}` 모델을 두고 `list[ResultWarning]` 으로 받는 편이 낫다.
- **`budgets_override` 가 `EngineBuildMeta` 에만 있다.** `engine_id` 재계산에 필요해서 넣은 것은 타당하나(docstring 에 사유 기재됨), §9.1 `meta` 에는 나가지 않는다. 예산을 덮어쓴 엔진과 아닌 엔진의 결과가 출력만 봐서는 구분되지 않는다. `engine_id` 로는 구분되므로 P2 이슈다.

**판정: PASS (이중 정의는 설계 의도로 정리 필요, 경고 타입 붕괴는 비블로커).**

**⚠️ `_extract_error_code` 정규식은 SPEC S11 정신과 충돌한다.** `cli.py:31,42-51` 이 `ValidationError` 메시지에서 `\bE-[A-Z]+(?:-[A-Z_]+)+\b` 로 코드를 긁어낸다. 구현자는 docstring 에서 "SPEC §9.1 은 `EngineResult.error.code` 얘기이고 이건 CLI 표시용" 이라고 방어했지만, 세 가지 이유로 받아들이기 어렵다.

1. **출력 모양이 계약과 동일하다.** `_echo_error` 는 `{"status":"ERROR","error":{"code","message","details"}}` 를 낸다 — SPEC §9.1 `EngineResult` 의 error 봉투와 같은 형태다. 소비자(QA 스크립트, 통합 테스트)는 이것을 계약으로 읽는다.
2. **정규식이 실제로 오답을 낸다(실측).** `fdt run --mode GOAL --out …`(params 없음) 을 주면 pydantic 이 `goal_type / Field required [type=missing]` 를 내는데 **이 메시지에는 `E-…` 문자열이 없어** 정규식이 실패하고 폴백 `E-REQ-INVALID` 가 나간다. SPEC §8.1 은 "필수 파라미터 누락은 `E-REQ-MISSING`" 이라고 못박았으므로 **계약 위반**이다. 반대로 `--params '{"goal_type":"BALANCE","target_amount":100}'`(target_date 누락)은 모델 validator 가 코드를 문자열에 태워 보내므로 `E-REQ-MISSING` 이 정확히 나온다 — 즉 **같은 종류의 실패가 어디서 걸리느냐에 따라 코드가 달라진다.** 또 오류가 여럿일 때 첫 매치만 집는다(`--horizon 400 --n-paths 50` → `2 validation errors` 인데 코드는 하나). `--mode GOAL --horizon 400 --params '{…target_date 누락}'` 에서는 **horizon 오류가 통째로 사라지고** `E-REQ-MISSING` 만 남는다.
3. **근본 원인은 검증 지점이 코드를 잃는 것**이다. `ModeRequest`/`TwinInput` 이 `ValueError(f"{CODE}: …")` 로 코드를 **문자열에 태워 보내기 때문에** 호출자가 파싱할 수밖에 없다. 옳은 수정은 CLI 가 아니라 스키마 쪽이다: 검증 지점에서 `FdtError(code=…)` 를 던지거나(pydantic v2 는 validator 안에서 임의 예외를 감싸므로 `ValidationError.errors()[i]["ctx"]["error"]` 로 원 예외에 접근 가능), 최소한 `ctx` 에 코드를 구조화해 실어야 한다. 그때 CLI 의 정규식은 통째로 삭제된다. → **S39**

경미: `inspect` 출력 `미결제(issued_unpaid)=82,700원건수=1` 에 공백 누락(`cli.py:177`).

### 함정 (반드시 읽을 것)

1. **큐에 대출이자가 두 번 들어 있다(B3).** B 프로필로 시뮬을 돌리면 매달 68,000원이 두 번 빠진다. 블로커가 고쳐지기 전에 시뮬 결과를 `ground_truth` 와 비교하면 원인 없는 편차를 쫓게 된다. **W6 착수 전 B3 를 먼저 고칠 것.**
2. **`payday_boost`·`pre_payday_damp` 는 A/B/D 에서는 신뢰할 만하지만(8시드 평균 편차 ≤ 0.08) C 에서는 클립에 붙어 있다**(2.0 / 1.3). C 백테스트가 안 맞아도 시뮬레이터 버그가 아닐 수 있다. SPEC §12 가 C 의 sMAPE 기준을 0.40 으로 느슨하게 잡은 것과 같은 맥락이다.
3. **`card_share` 와 `daily_rate` 는 "거절되지 않고 살아남은 소비" 로 추정된 값이다.** SPEC §11 이 잔액 부족 시 체크 거절을 원장에 남기지 않기 때문에, 잔액이 얇은 사용자일수록 `daily_rate` 는 과소, `card_share` 는 과대 추정된다(C 편의점 0.32 → 0.65). 시뮬레이터가 `suppressed_demand` 를 다시 누적하면 **같은 억제를 두 번 세는 셈**이 된다. 정답 분포와의 비교는 이 편향을 감안해서 읽을 것.
4. **`기타` 봉투(id 7)의 `amount_mu` 는 돌발에 오염돼 있다.** 6단계 돌발이 `기타` 로 들어가고 5단계 일상 소비도 `기타` 로 들어가므로, 두 분포가 겹쳐 `기타` 지출이 과대 생성될 소지가 있다.
5. **`elasticity` 는 상·하한에 자주 붙는다.** 특히 필수 봉투(교통비·의료·건강·편의점)에서 2.00 이나 0.50 이 나오면 SPEC S24 의도와 반대다. `elasticity_gate` 의 기준 잔여율은 **그 달 1일~전날 누적 / 예산 < 0.2** 이고(S36), 예산은 `state.envelopes[].budget`(A/B/C 는 PROPOSED, D 는 CONFIRMED)이다.
6. **`state.committed` 의 due 는 `(as_of, as_of+90]` 구간뿐이다.** `horizon_days` 가 90 을 넘는 요청(SPEC §8.1 은 365 까지 허용)에서는 큐가 비어 고정비가 사라진다. `build_committed_queue(horizon_cap=…)` 를 다시 부르거나 시뮬레이터가 월 반복을 자체 연장해야 한다 — **어느 쪽인지 W6 이 정하고 SPEC 에 적을 것.**
7. **`Engine.fork()` 는 `meta` 를 공유한다(N15).** 분기 시뮬이 경고를 추가하면 기준 엔진이 오염된다. `overrides` 를 쓰거나 `meta` 도 복사할 것.
8. **원장은 `as_of` 에서 잘려 있다.** `engine.ledger` 를 `twin.as_of` 기준이라고 가정하는 코드를 새로 쓰지 말 것(B1·B2 가 정확히 그 실수다).
9. `MODE_RUNNERS` 는 빈 dict 이고 시그니처는 `Callable[[Engine, ModeRequest], ResultUnion]` 이다. 등록만 하면 `Engine.run()` 이 `FdtError`/`ValidationError` 를 잡아 `status=ERROR` 봉투로 만들어 준다 — 모드 러너 안에서 예외를 삼키지 말 것.

## 결론

Phase 2 는 **핵심 수치 계약(잔액·카드 상태·큐 손계산·요일 배수·재현성·성능)을 실측으로 전부 통과**했고, 코드 품질(타입·린트·커버리지 94%·아키텍처 격리·docstring 의 SPEC 절 참조)도 앞선 두 단계보다 확실히 낫다. W1/W2 의 블로커 세 건(카드 요일 무시, 더치 입금 INCOME 오분류, 고정비 오분류)이 전부 해소된 것도 확인했다.

다만 **홀드아웃 경로(B1·B2)가 깨져 있어 Phase 7 평가 전체가 그 위에 서 있고**, **대출이자 이중 계상(B3)은 Phase 3 시뮬레이터의 정답 대조를 직접 오염**시킨다. 셋 다 원인이 명확하고 수정 범위가 좁으므로(각 5~15줄), **W6 착수 전에 고치고 회귀 테스트를 붙일 것을 권고**한다. 특히 B1 은 `--omit-opening-balance` 로 생성한 프로필에서 `as_of − 30` liquidity 를 `ground_truth` 와 비교하는 테스트 한 건이면 영구히 막힌다.
