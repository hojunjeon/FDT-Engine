- **(e) 잔액 부족 체크 결제 거절이 원장에 남지 않는가** - **PASS**. `_spend_one` 의 else 분기(`generator.py:568-573`)와 `_step_fixed` 의 else 분기(`generator.py:398-401`), LOAN else 분기(`generator.py:420-423`) 는 모두 `gt["declined_debits"]` 에만 적재하고 `_add_tx` 를 호출하지 않는다. **`break` 해석 판정.** SPEC §7.2 4단계 문구는 "오래된 것부터, `cash ≥ total` 이면 차감·제거, 부족하면 `card_shortfall[p]=True`, 청구서 유지" 다. 뒤 청구서를 계속 시도하는지 멈추는지에 대한 서술이 **없다**. 구현자의 `break`(`generator.py:490-491`)는 실무 규칙(연체 중이면 후속 청구서도 못 나간다)으로 방어 가능하고, 현재 seed 에서는 동시 미결제 사례가 0건이라 결과 차이도 없다. 그러나 W6 시뮬레이터가 같은 규칙을 벡터화해야 하므로 **어느 쪽이든 SPEC 에 한 줄로 명문화해야 한다** → **S16**. 리뷰어 권고는 `break` 유지(오래된 청구서가 막히면 그날은 해당 카드 결제를 중단)이며, 이유는 (1) 실무 정합, (2) 벡터화 시 경로별 분기가 하나로 줄어 구현이 단순, (3) `payment_risks` 의 결제 이벤트 순서가 결정론적으로 유지된다는 점이다.

### 5. `confirm_status` 90/10 을 모든 거래에 적용 - **주의** (지금은 무해, 규약 필요)

`generator.py:246`(`_add_tx`)이 `_confirm_status()`(`generator.py:193-194`, `rng.random() < 0.9 ? AUTO : PENDING`)를 **모든** 거래에 적용한다. 실측 결과 수입·고정비·카드대금에도 PENDING 이 붙는다: A(INCOME 1, FIXED 2, CARD_BILL 4), B(INCOME 1, FIXED 1, CARD_BILL 4), C(INCOME 1, CARD_BILL 3), D(FIXED 4, CARD_BILL 2).

문제가 되는 곳: **의미론과 Phase 2 이후의 재사용**이다. `confirm_status` 는 "사용자가 세분류를 확인했는가" 이므로 급여 입금·자동이체 카드대금이 PENDING 인 것은 데이터로서 거짓이고, RISK 의 "우려 결제" 나 facts 문장이 이 필드를 다시 쓰면 오작동한다. C 프로필은 `unconfirmed_count = 0` 이라 Phase 3 의 이 지표 테스트가 공허하게 통과할 위험도 있다. → **N5**, **S20**

### 10. 착수 가능성 판정

**Phase 2(State · Behavior) 착수 전 블로커 5건**(B1~B5), **비블로커 13건**(N1~N13).

B1·B2 는 Phase 2 의 완료 조건을 직접 깬다. B1 은 "B 프로필 화요일 as_of 에서 카드 미청구·미결제 due·금액이 수작업 계산과 일치"(§5.4 큐)를, B2 는 "Behavior: A 규칙적 수입 25일, C 불규칙"(§6.6 수입 일정)을 깬다 - B 는 지금 원장만 보면 불규칙 수입자로 판정된다. B3 는 Phase 2 State 의 `spent`·`propose_budgets` 를 그대로 틀리게 만든다. B5 는 A 프로필의 잔액 궤적이 시뮬레이터로 재현 불가능하다는 뜻이므로, Phase 2 의 약정 큐 설계 전에 SPEC 결정이 필요하다. B4 는 위 세 건이 재발하는 것을 막는 게이트다.

N1·N2(프로필 캘리브레이션)는 Phase 3(FORECAST/RISK)·Phase 4(GOAL) 착수 전까지, N3(`pre_payday_damp`)는 Phase 3 시뮬레이터 착수 전까지 반드시 결론이 나야 한다.

### B1. 카드 출금이 `withdrawal_weekday` 를 무시한다 (연체 판정 기준 오류)

- 파일: `fdt/gen/generator.py:456-491` (`_step_card_withdraw`), 특히 465-469행
- 증상: 카드 21(`withdrawal_weekday: 5` 토)이 6개월 동안 **한 번도 토요일에 결제되지 않았다.** 전 청구서 53건의 결제 lag 분포가 `{1일:50, 2일:1, 4일:2}` 로, 전부 월요일 발행 다음 날(화요일)이다. `card_shortfalls` 14건 중 6건(`04-07~09`, `07-07~09`)이 카드 21 의 화·수·목 시도로, **존재해서는 안 되는 이벤트**다.
- 원인: 시도 조건이 `due_today = d.weekday() == card.withdrawal_weekday` **또는** `overdue = any(b.billing_date < d for b in unpaid)` 다. `overdue` 가 "발행일이 지났는가" 를 보므로, 월요일 발행 청구서는 화요일부터 무조건 연체로 간주되어 그 카드의 예정 출금일과 무관하게 결제된다.
- 왜 블로커:
  1. SPEC §11 "B: 카드 2장(**화·토** 출금)" 이 생성 데이터에 존재하지 않는다.
  2. SPEC §5.4 약정 큐가 "카드대금(미청구) = 다음 월요일 발행 후 첫 `withdrawal_weekday`", "카드대금(미결제) = 다음 `withdrawal_weekday`(as_of 포함)" 로 due 를 계산한다. Phase 2 State 는 카드 21 의 due 를 토요일로 내는데 원장에는 화요일 결제만 있으니, PLAN Phase 2 완료 조건("B 프로필 화요일 as_of 에서 큐 due·금액이 수작업 계산과 일치")이 즉시 실패한다.
  3. Phase 3 시뮬레이터가 SPEC §7.2 4단계를 올바르게 구현하면 생성기와 어긋나 B 의 백테스트 sMAPE(≤ 0.25)와 RISK 캘리브레이션이 무너진다. PLAN §10 P1 리스크가 실현된 상태다.
- 수정 지시문:
  `_step_card_withdraw` 의 시도 조건을 "예정 출금일" 기준으로 바꾼다. 청구서별로 **최초 예정 출금일** `first_due(billing) = billing.billing_date 이후(당일 포함) 첫 d.weekday() == card.withdrawal_weekday 인 날` 을 계산하고, 그날 이전에는 그 청구서를 시도하지 않는다. 구체적으로 465-469행을 다음 규칙으로 대체하라.

  ```
  attemptable = [b for b in unpaid if _first_due(b, card.withdrawal_weekday) <= d]
  if not attemptable: return
  # 이후 오래된 것부터 시도. 부족하면 card_shortfalls 기록 후 break (S16 확정 규칙)
  ```

  `_first_due` 는 `billing_date` 부터 최대 7일 전진하며 `weekday() == withdrawal_weekday` 인 첫 날을 반환하는 순수 함수로 만들고, `withdrawal_weekday` 가 월요일(0)인 카드에서 발행 당일이 곧 예정일이 되는 경계를 단위 테스트로 고정하라(현재 4 프로필에는 월요일 출금 카드가 없어 이 경계가 한 번도 밟히지 않는다). 수정 후 `fdt gen --profile all --seed 7` 로 `data/seed/` 를 재생성하고, 카드 21 의 결제 lag 이 5일(월→토)로 나오는지, B 의 `card_shortfalls` 개수를 재측정해 6개월 3~8건 범위인지 확인해 리뷰에 기록하라. 같은 규칙을 SPEC §7.2 4단계 문구로도 확정한다(**S16**).

### B2. 더치페이 입금이 `INCOME` 으로 분류되어 봉투를 줄이지 않고 수입 일정을 오염시킨다

     if tx.tx_type == TxType.DEPOSIT:

### B3. 고정비 매칭 오분류로 봉투 월 순지출이 `envelope_true_spend` 와 어긋난다 (PLAN Phase 1 완료 조건 위반)

- 파일: `fdt/engine/ledger.py:302-318` (`_match_fixed_expense`), 306-311행
- 증상 (실측): PLAN Phase 1 완료 조건 "봉투 월 순지출 == `envelope_true_spend`" 가 **A 7/7월만 통과, B 5/7, C 3/7, D 2/7**. 차액은 오분류된 소비 거래 금액과 원 단위까지 일치한다.

  | 프로필 | `flow_hint` 없는데 `FIXED` 로 판정된 건수 | 합계 | 예 |
  | --- | --- | --- | --- |
  | B | 3 | 229,700 | `2026-08-17 무신사 110,700`(세분류 15 → 봉투 5) → 봉투 5 가 478,600 대신 367,900 |
  | C | 5 | 221,700 | `2026-04-03 스타벅스 45,100`(세분류 2 → 봉투 1) → 봉투 1 이 1,055,100 대신 1,010,000 |
  | D | 7 | 102,300 | `2026-03-16 유니클로 23,700`(세분류 14 → 봉투 5) → 그 달 봉투 5 가 **통째로 사라짐**(23,700 → 0) |

- 원인: 매칭 조건이 `(계좌 또는 카드) AND 금액 ±10% AND payment_day ±3일` 뿐이다. 두 구멍이 있다.
  1. `account_matches = tx.account_id == fx.withdrawal_account_id`. 생성기는 CARD 거래에도 `account_id` 를 카드의 출금 계좌로 채워 넣는다(`generator.py:551`). 따라서 평범한 카드 소비가 계좌형 고정비와 매칭된다.
  2. `card_matches = tx.card_id == fx.card_id`. D 의 카드형 구독(넷플릭스 17,000 / 스포티파이 10,900 / 유튜브 14,900)과 **같은 카드로 결제한 1~2만원대 소비 전부**가 금액·날짜만 맞으면 매칭된다. D 의 오분류 7건이 정확히 이 유형이다.
  즉 "소비인지 고정비인지" 를 가르는 판별자가 없다. 실무 판별자는 **`subcategory_id` 의 존재**다 - 생성기의 고정비·카드대금은 `subcategory_id` 가 `None` 이고 소비는 항상 값이 있다.
- 왜 블로커: Phase 2 State 의 `spent`(§5.3), `propose_budgets`(§5.5), Behavior 의 `daily_rate`·`amount_mu`·`card_share`(§6, `SPEND` 만 사용)가 전부 이 원장에서 파생된다. 봉투 지출이 최대 100% 누락되는 달이 있는 상태로 Phase 2 를 쌓으면 어디서 틀렸는지 추적이 불가능해진다.
- 수정 지시문:
  `_match_fixed_expense` 앞에 판별 가드를 넣어라. SPEC §5.2 규칙 3 에 다음 두 조건을 추가하고 코드도 함께 고친다(SPEC 수정 **S17** 동반).
  1. `tx.subcategory_id is not None` 이면 고정비 후보에서 제외한다(세분류가 붙은 거래는 소비다).
  2. 계좌형 고정비 매칭은 `tx.tx_type in (WITHDRAW, TRANSFER)` 로 한정한다. `tx_type == CARD` 인 거래는 **`fx.card_id` 가 있는 고정비와만** 매칭하고 `fx.withdrawal_account_id` 경로로는 매칭하지 않는다.
  3. 보강으로 `fx.name` 과 `tx.merchant_name_raw` 의 동등 비교를 통과하면 1·2번 가드를 우회해 매칭시키는 경로를 남겨 두어라(LIVE 데이터에서 세분류가 붙은 고정비가 들어올 수 있다).

  수정 후 4 프로필 × 전 월에 대해 `envelope_net_spend == envelope_true_spend` 가 성립하는지 확인하고, 성립하지 않는 달이 남으면 그 차액의 원인을 이 리뷰와 같은 방식(오분류 거래 특정)으로 규명해 기록하라. `test_ledger.py:274-292` 의 허용 오차 경계 테스트는 유지하되, "세분류가 붙은 같은 금액·같은 날짜의 카드 소비는 FIXED 가 아니다" 를 새 케이스로 추가하라.

### N3. `pre_payday_damp` 가 SPEC §7.2 λ 식과 §6 추정 표에 없다 (기한: Phase 3 착수 전)

- 파일: `fdt/gen/generator.py:500-507` (`_cycle_mult`), 4 프로필 YAML 의 `hidden.pre_payday_damp`
- 근거: 생성기는 `cm = payday_boost(수입 후 7일) × pre_payday_damp(다음 수입 5일 전)` 을 λ 에 곱한다. SPEC §7.2 5단계 식은 `λ = daily_rate × weekday_mult[wd] × boost × elasticity_gate` 로 단일 `boost` 만 두고, §6 추정 표에도 `payday_boost` 만 있다. 한편 SPEC §11 은 `pre_payday_damp` 를 "생성기가 엔진에 숨기는 변수" 로 명시했다 - §11 과 §7.2/§6 이 서로 모순이다.
- 영향: §6 의 `payday_boost` 추정(수입 후 7일 일평균 / 그 외 일평균)은 분모에 damp 구간이 섞이므로 실제 `payday_boost` 보다 큰 값을 낸다. A(1.15 × 0.9), B(1.3 × 0.9), D(1.1 × 0.9) 는 damp 가 있고 C(1.0)는 없다. 편향 방향이 프로필마다 달라 백테스트 잔차 해석이 어려워진다.
- 지시문: S23 으로 SPEC 을 먼저 확정하라. 두 갈래다.
  - **(권장) `boost` 를 복합 계수로 명문화한다.** §7.2 5단계의 `boost` 를 `boost(d) = payday_boost^[수입 후 7일] × pre_payday_damp^[다음 수입 5일 전]` 로 정의하고, §6 표에 `pre_payday_damp` 행("다음 수입 5일 전 일평균 / 그 외 일평균, 클립 [0.5, 1.3], 표본 10일 미만이면 1.0")을 추가한다. 그러면 시뮬레이터·Behavior·생성기가 같은 식을 쓰고 숨김 변수 목록에서 `pre_payday_damp` 를 빼야 한다.
  - **(대안) 숨김 유지.** §7.2 5단계에 "생성기는 추가로 미공개 주기 계수를 곱할 수 있다" 를 명시하고 §12 의 백테스트 기준을 그 편향을 감안해 정한다. 권장하지 않는다 - 재현 불가능한 편향을 계약으로 승인하는 셈이다.

### N4. `elasticity` 가 봉투별이 아니라 프로필 스칼라 하나다

- 파일: `fdt/gen/generator.py:493-498` (`_elasticity_gate`), 4 프로필 YAML `hidden.elasticity`

- 지시문: 프로필 YAML 의 `hidden.elasticity` 를 봉투별 dict 로 확장하라(`hidden.elasticity: {외식: 0.8, 교통비: 1.0, ...}`). 하위 호환으로 스칼라도 받되(`float` 이면 전 봉투 동일값으로 확장), 4 프로필은 봉투별로 값을 흩뿌려 유연 봉투(외식·쇼핑·취미·여가·기타)는 프로필 대표값 부근, 필수 봉투(교통비·의료·건강·편의점·마트·잡화)는 1.0 에 가깝게 두어라 - 필수 지출은 예산이 말라도 잘 줄지 않는다는 현실 및 SPEC §8.4 의 "필수 봉투 하한 80%" 와 정합한다. SPEC §11 의 프로필 표에 적힌 "탄력도 0.75 / 1.4" 는 유연 봉투 대표값으로 재해석하고 그 뜻을 SPEC 에 한 줄 적어라(S24).

### N7. `flow_hint` 우선이 취소 분할·TRANSFER 상대 레코드를 통째로 건너뛴다 (잠재)

### N8. `declined_debits` 가 `unpaid_obligation` 과 `suppressed_demand` 를 구분하지 않는다

### N9. `envelope_net_spend` 의 `abs()` 가 부호를 삼킨다
